# 幸运摇摇球 · 开发心得

> 一个把手机桌面所有应用装进摇奖机、靠运气决定你打开哪个 App 的安卓小工具。
> 版本 v1.1（versionCode 2）｜包名 `com.workbuddy.lottery`｜minSdk 26 / targetSdk 34
> 安装包体积 2.4 MB｜Kotlin 代码 1090 行｜**零图片资源、零音频资源、零权限**

---

## 一、为什么开发这个（开发需求）

### 1. 痛点：一百多个 App，常用的只有五个

手机里装着上百个应用，每天真正打开的其实就那五六个，剩下的全是“装的时候觉得会用、装完再没点过”。桌面翻两遍找不到想要的东西，最后还是会点回最上面那几个图标。

选择困难到最后变成一种无聊的重复。**既然每天的选择本来就没什么意义，不如把它变成一个游戏。**

### 2. 原始需求（一句话版）

> 做一个安卓 App：把手机桌面上的所有应用装进彩色小球，拉动摇杆后球在机器里翻滚，摇完从出奖口掉出几颗球，点球就能启动对应的应用。

拆开看，这个需求里其实包含了四个必须同时成立的点：

1. **球要装真应用**——不是预设的假数据，换一台手机就得是那台手机的应用；
2. **摇杆要能拉**——拉下去才有反应，不能点一下按钮了事；
3. **球要真的翻滚**——要有碰撞、有惯性、有随机性，不能是贴图转圈；
4. **只有摇出来的球能点开应用**——机舱里还在转的球点不动。

第 4 点是后来才补上的。第一版做出来，机舱里的球也能点，用户立刻指出来“这是不对的，要只有摇奖掉出来的应用才能启动”。这条反馈本质上是在说：**摇奖机必须遵守摇奖机的规则，否则它只是个好看的图标墙。**

### 3. 需求拆解

| 类型 | 需求 | 实现方式 |
|---|---|---|
| 功能 | 读取本机全部可启动应用（图标 + 名称 + 包名） | `queryIntentActivities(MAIN/LAUNCHER)` |
| 功能 | 应用装进球体，球在舱内漂浮 | 每颗球绑定精灵 `Bitmap` + 应用图标 |
| 功能 | 下拉摇杆触发翻滚 | 触摸判定 + 三态状态机 |
| 功能 | 摇完掉出固定数量球，可点击启动 | 出球门 + 奖池槽 + `Intent` 启动 |
| 体验 | 音效反馈 | 运行时合成 4 种音效 |
| 体验 | 竖屏全屏、常亮、不被打断 | 沉浸式 + `KEEP_SCREEN_ON` |
| 约束 | 不联网、不申请敏感权限 | 零权限清单 |
| 约束 | 体积要小，能随手发给别人 | 零素材，APK 控制在 3 MB 内 |

### 4. 明确的边界：这个 App 不做什么

需求写清楚“不做什么”，比写清楚“做什么”更能省时间。以下是我主动砍掉的功能：

- **不做推荐**——不统计你点了哪个球，不做“常打开的应用加权”，因为一旦有了算法，运气就不纯粹了；
- **不做摇奖历史**——不记录、不排行、不画图表；
- **不做账号与云同步**——整个 App 没有 `INTERNET` 权限，也不打算有；
- **不做桌面小组件**——第一版的复杂度撑不住，先把主界面做扎实；
- **不做多语言**——只面向中文用户。

最后一条特别重要。一个“把 App 装进球里摇出来”的小工具，功能越少，手感越容易被做透。**把力气花在物理参数和视觉质感上，比多加十个功能更能让人愿意留着它。**

### 5. 由此推出的技术目标

需求里那句“球要真的翻滚”，直接把技术路线定死了：**摇出来的结果必须像真的，不能是假动画配个随机数。**

所以整个项目的技术目标只有一句话：

> 用代码把一台实体摇奖机的手感还原出来——没有美术素材，没有物理引擎，全部靠 Canvas 和数值计算。

这也是后面所有设计取舍的起点：为什么全自绘、为什么自己写碰撞、为什么音效要现场合成。

## 二、架构：一个 View 装下整个应用

整个 App 只有三个类，职责切得很干净：

| 文件 | 行数 | 职责 |
|---|---|---|
| `MainActivity.kt` | 72 | 读取应用列表、全屏沉浸、挂载 View |
| `LotteryView.kt` | 823 | 几何布局、物理模拟、全量 Canvas 绘制、触摸交互 |
| `SfxEngine.kt` | 195 | 运行时合成音效、SoundPool 播放 |

没有 Fragment、没有 ViewModel、没有 DI、没有网络库。依赖只有 `core-ktx` 和 `appcompat` 两个。

**为什么全自绘**：如果走常规的"图片素材 + 布局"路线，机框、玻璃舱、彩球、门板至少需要二十多个切图，还得适配各种屏幕密度。全自绘的好处是——**任何分辨率下都锐利**，改一个颜色只需要改一个常量。

## 三、物理：让 50 颗球"像活的"

这是整个项目里最花心思的部分。球舱里同时存在 50 颗球，每帧要做的事分三层。

### 1. 三种状态机

```
IDLE（待机，球轻微漂浮）
  └─ 拉摇杆 → SPINNING（涡流翻滚 2.4 秒）
        └─ 计时结束 → DROPPING（每 360ms 掉一颗，共 5 颗）
              └─ 掉完 → IDLE
```

### 2. 涡流力而非"旋转坐标"

最开始我试过直接让球绕中心做圆周运动——看起来像洗衣机甩干，非常假。真正有效的是**切向加速度 + 随机扰动**：

```kotlin
// 涡流切向力：垂直于半径方向推
b.vx += (-dy / dist) * dp(2900f) * dt
b.vy += ( dx / dist) * dp(2900f) * dt
// 随机扰动 + 偏上的抛力（模拟鼓风机把球往上顶）
b.vx += (rnd.nextFloat() - 0.5f)  * dp(2200f) * dt
b.vy += (rnd.nextFloat() - 0.85f) * dp(2200f) * dt
limitSpeed(b, dp(1050f))   // 必须有速度上限，否则球会穿墙
```

关键在于 `limitSpeed()`。没有它，球在涡流里会不断加速直到一帧跨越整个舱壁，出现穿模。**给一个 1050dp/s 的硬上限，是保证稳定性的最低成本方案。**

### 3. 每帧 1225 次球球碰撞

50 颗球两两比较是 `C(50,2) = 1225` 对，60fps 下每秒约 7.3 万次检测。这在手机上完全跑得动，前提是**不要用引擎、不要创建对象**——纯标量运算，没有临时 Vector 对象，GC 压力为零。

```kotlin
val overlap = (rr - d) * 0.5f      // 位置分离，各退一半
a.x -= nx * overlap; b.x += nx * overlap
val rel = (b.vx - a.vx) * nx + (b.vy - a.vy) * ny
if (rel < 0) {                     // 只在相互接近时才施加冲量
    val imp = rel * 0.92f          // 0.92 = 球球接近完全弹性
    a.vx += nx * imp; b.vx -= nx * imp
}
```

三个不同的反弹系数，是让手感"分层"的细节：

| 碰撞对象 | 系数 | 效果 |
|---|---|---|
| 舱壁 | 0.82 | 有弹性但不夸张 |
| 舱底 | 0.55 | 明显"沉"，球会滚而不是跳 |
| 球与球 | 0.92 | 接近弹性，撞击清脆 |

### 4. 出球门：从色块到双开门

第一版出球口就是个深色矩形。用户第一句反馈是"把这里的代表洞口的色块去掉，改成一个可以开合的门"。

改法是把门拆成左右两片叶子，各自绕外侧边缘旋转，用 `doorT ∈ [0,1]` 做缓动：

```kotlin
val doorTarget = if (state == State.DROPPING) 1f else 0f
doorT += (doorTarget - doorT) * min(1f, dt * 9f)   // 指数缓动，有惯性感
```

叶子滑出时会与机框边缘发生视觉冲突，所以两片叶子的位移必须**限制在半个门宽以内**，并且要在机框内裁切，否则会看到门板"飘"到机身外面。

另一个坑：球必须真的穿过门口才被销毁。判据是 `abs(b.x - gateX) < gateHalf`，同时球的下沿要越过舱底——少了这个条件，球会在门口上方凭空消失。

## 四、音效：不打包一个音频文件

素材是 APK 里最容易被忽略的体积来源。四个音效（转动的摩擦声、出球的"啵"、落定的胜利音、点击反馈）如果找素材，少说也要几百 KB，还要处理版权。

我的做法是**运行时合成 WAV**：首次启动时用正弦波和噪声算出采样点，写成标准 WAV 字节流放进 `cacheDir`，再交给 `SoundPool` 加载。

```kotlin
private const val SR = 22050          // 22.05kHz 足够，体积减半
private val vols = mapOf("spin" to 0.55f, "pop" to 0.75f,
                         "win" to 0.70f, "tap" to 0.45f)
```

几个实用细节：

- **每个音效单独调音量**。统一音量一定会有问题：翻滚动效应该是背景，出球声必须是前景。
- **播放速率加随机抖动**（`rate` 在 0.5~2.0 之间），同一个音效连续响五次不会听出是同一段循环。
- **合成失败要能降级**。整个 `ensureWav()` 包在 try-catch 里，写文件失败就直接跳过——音效坏掉不能影响游戏本体。

## 五、零权限，是有代价的设计

`AndroidManifest.xml` 里没有 `INTERNET`，没有 `QUERY_ALL_PACKAGES`。这件事在开发阶段让我多花了半天。

Android 11 起有软件包可见性限制，`queryIntentActivities()` 默认只能看到"自己"。解决办法不是申请 `QUERY_ALL_PACKAGES`（上架会被审查），而是用 **intent 查询作为隐式声明**：

```kotlin
val intent = Intent(Intent.ACTION_MAIN).addCategory(Intent.CATEGORY_LAUNCHER)
val infos = if (SDK_INT >= 33)
    pm.queryIntentActivities(intent, ResolveInfoFlags.of(0))
else pm.queryIntentActivities(intent, 0)
```

查 `MAIN/LAUNCHER` 类型的 intent，本身就是"我需要看到有桌面入口的应用"的合法声明，不需要任何权限，也能拿到全部可启动应用。这比申请 `QUERY_ALL_PACKAGES` 干净得多，上架时不用写任何隐私说明。

**零权限带来的直接收益**：隐私政策几乎不用写，用户第一次打开没有任何弹窗，酷安、应用宝这类渠道的审核阻力极低。

## 六、构建环境：从零搭一条国内可用的链路

这台机器一开始什么都没有——没有 JDK、没有 Android SDK、没有 Gradle。国外源下载动辄几小时，所以每一步都换成国内镜像：

| 组件 | 版本 | 镜像源 |
|---|---|---|
| JDK | 17 | 华为云 |
| Gradle | 8.7 | 腾讯云 |
| Android SDK | Platform 34 + Build-Tools 34 | 阿里云 Maven |

过程中踩到的两个硬坑：

### 1. 中文路径被 AGP 直接拒绝

项目路径 `C:\...\app 摇奖` 含中文，AGP 启动时报路径校验失败。解法是在 `gradle.properties` 加一行：

```properties
android.overridePathCheck=true
```

这行相当于明确告诉 AGP"我知道路径非 ASCII，别拦我"。对于 Windows 中文用户名环境，这是必备项。

### 2. Gradle 里的 dp() 只收 Float

绘制代码里到处是 `dp(20)` 这种写法，但 `private fun dp(v: Float) = v * density` 只接受 Float，Kotlin 不会自动把 Int 字面量转成 Float。报错信息指向的位置又很分散。

最后的处理是**批量改成 `dp(20f)`**，顺带把颜色常量统一成 `.toInt()` 形式——因为 `0xFFF7CE5B` 在 Kotlin 里被推断成 `Long`，而 `Paint.color` 要 `Int`，不加 `.toInt()` 全部编译不过。这两个问题在 Kotlin 写 Android 图形代码时几乎必然遇到。

## 七、v1.0 → v1.1：反馈驱动的七轮迭代

这个版本的所有改动都来自真实使用反馈，记录如下：

| # | 反馈 | 改动 | 技术点 |
|---|---|---|---|
| 1 | UI 太丑，掉出来的图标太小 | 重做配色与布局，出球区改成 2×4 大奖球槽 | 全部几何改为按屏幕比例计算 |
| 2 | 机内没掉出来的球也能点开应用 | 点击只响应奖池球 | `handleTap()` 遍历 tray 而非 balls |
| 3 | 加一点音效 | 合成四种音效 | 见第四节 |
| 4 | 每批 24 太少、出 8 太多 | 改为每批 50 颗、每局出 5 颗 | `BATCH_SIZE=50`、`COLS=5` |
| 5 | 状态文字和摇杆文字重叠 | 缩字号、换文案、摇杆字改图形 | 布局分层，文字与控件不共用区域 |
| 6 | 出球口色块改开合门 | 双开门动画 | 见第三节第 4 点 |
| 7 | 图标太丑、名字要改 | 改名为「幸运摇摇球」+ 立体玻璃球机图标 | 自适应矢量图标（纯 XML，无 PNG） |

**一个反直觉的结论**：第 4 条改完之后，手感明显变好了。球从 24 颗加到 50 颗，舱内密度上去了，碰撞更频繁，翻滚看起来才"满"。**球太少会让物理模拟显得空**——即使每颗球的运动都算对了，视觉上也不像一台装满球的机器。

## 八、签名与分发

- 正式签名使用自建 keystore（`release.keystore`，别名 `lottery`），APK 已用 apksigner 验证通过
- v1.1 签名后的 MD5 与线上分发文件一致，可直接覆盖安装 v1.0
- 分发走自建静态页，下载按钮自动携带 sharecode，避免链接被爬或被白嫖流量
- 上架酷安的材料（图标、截图、简介、隐私政策）已全部备齐，只差实名认证

**分发的现实**：Google Play 之外，国内安卓分发基本走酷安、应用宝、各大手机厂商商店，每一家都要求实名 + 软著或备案。一个没有主体的个人开发者，最快的路径是酷安（个人可发，审核相对宽松）。

## 九、如果重做一次，我会改什么

1. **物理用固定步长**。现在是按帧间隔 `dt` 积分，高刷屏（120Hz）和 60Hz 的手感会略有差异。固定 1/60 秒步长 + 累加器，能让所有设备表现一致。
2. **球的自绘精灵缓存到内存池**。现在 `sphereSprite()` 每次重建 Bitmap，切换批次时会有一瞬间的卡顿。改成按颜色懒加载 + 复用，能彻底消除。
3. **音效合成放到后台线程**。首次启动时合成四个 WAV 大约要几十毫秒，压在 `init` 里会让首屏略慢。
4. **物理参数做成可调面板**。调手感那几天，每次都要改常量、重新编译、装 APK，一轮五分钟。如果做一个长按标题弹出滑杆的调试面板，效率能高十倍。

## 十、这个项目教会我的

**"手感"不是美术问题，是数值问题。** 摇奖机好不好玩，取决于涡流力多大、速度上限多高、反弹系数是 0.55 还是 0.82——这些数字调对了，纯代码画的东西也会有重量感；调错了，再精细的贴图也是塑料玩具。

**约束会逼出更好的方案。** 零权限逼出了 intent 查询的干净写法，零素材逼出了运行时合成音效，没有设计资源逼出了全自绘。如果一开始什么都允许，这个 App 大概率会变成一个塞满切图、申请一堆权限的臃肿东西。

**反馈比规划有价值。** 六轮迭代没有一轮是我自己想到的，全部来自"这里丑""这个能点不对""字重叠了"。**做出来给人用，比自己想十遍都有用。**
